# Output templates

Two target shapes. Each has a fixed structure so the output is consistent across diagrams. Substitute the `{{placeholders}}` with content extracted per `extraction.md`.

## Template 1: `specs.md` (technical specification)

Audience: engineers who will implement, test, or maintain the process. Vocabulary: precise, exhaustive, unambiguous.

```markdown
# {{Process Name}}

> Technical specification generated from `{{source.bpmn}}` on {{date}}.
> Source process id: `{{process_id}}`

## 1. Overview

{{One paragraph describing what the process does. Pulled from bpmn:documentation
on the bpmn:process element if present, otherwise synthesized from the start
event name + first task name + end event name.}}

## 2. Actors and roles

{{For each pool}}
- **{{participant_name}}** — {{description, derived from name + responsibilities}}
{{/for each}}

{{For each lane within each pool}}
- **{{lane_name}}** ({{participant_name}}) — responsible for: {{list of tasks in this lane}}
{{/for each}}

## 3. Triggers

{{For each start event}}
- **{{start_event_name}}** ({{event_subtype, e.g. "message", "timer", "signal"}}) — {{description}}
{{/for each}}

## 4. Main flow (happy path)

The path from the most prominent start event to the most positive-sounding end event.

1. **{{actor_1}}** {{action_1}}.

2. **{{actor_2}}** {{action_2}}.
3. ...
N. **{{actor_n}}** {{final_action}}, ending in **{{end_event_name}}**.

## 5. Alternative flows

For each gateway in the main flow, the branches not taken become alternative flows.

### 5.1 {{Gateway name or "After step N"}} — {{branch condition}}

1. {{Re-narrate from the branch point to its end event}}

### 5.2 ...

## 6. Exception flows

Boundary events (timers, errors, escalations) attached to tasks in the main flow.

### 6.1 {{task_name}} — {{boundary_event_type}} ({{trigger}})

{{e.g. "If the Loan Officer does not complete *Review application* within 48 hours, the task is cancelled and the flow continues to *Escalate to Branch Manager*."}}

### 6.2 ...

## 7. Integration points

Cross-pool message flows. These are external API contracts.

| From | To | Message | Direction | Notes |
|---|---|---|---|---|
| {{src_pool}} | {{tgt_pool}} | {{message_name}} | sync/async | {{any extension data}} |

## 8. Data contracts

Data objects flowing through the process.

### 8.1 {{data_object_name}}

- **Created at:** step {{N}} ({{task_name}})
- **Read by:** steps {{M, P, ...}}
- **Schema:** {{if available from extensions, otherwise "[needs definition]"}}

## 9. End states (outcomes)

{{For each end event}}
- **{{end_event_name}}** ({{end_event_type}}) — {{narrative description of when this is reached}}
{{/for each}}

## 10. Acceptance criteria

Auto-derived from the structure. Each is a `Given-When-Then` derived from a flow path.

- **Given** {{precondition from start event}}
  **When** {{main flow happens}}
  **Then** the process ends in **{{positive end event}}** with {{output data}}.
- **Given** {{precondition}}
  **When** {{alternative flow condition}}
  **Then** the process ends in **{{alternative end event}}**.
- {{repeat for each terminal state}}

## 11. Open questions

{{Any ambiguities surfaced during translation: unnamed tasks, gateways without
condition expressions, dangling flows, missing data schemas. Listed as TODOs.}}

```

## Template 2: `prd.md` (product requirements document)

Audience: product managers, designers, stakeholders, executives. Vocabulary: outcomes, users, value.

```markdown
# PRD: {{Process Name}}

> Generated from `{{source.bpmn}}` on {{date}}. This PRD describes the
> product requirements for the {{Process Name}} workflow.

## Problem statement

{{One paragraph: what the user can't do today, and why this process matters.
Inferred from the process name + the start event name + the end event names.
If genuinely unclear from the diagram, surface as an open question instead
of inventing.}}

## Users and stakeholders

{{For each pool/lane that contains user tasks}}
- **{{role_name}}** — {{what they do in this process, in user-language not
  system-language}}
{{/for each}}

{{For each pool that is an external system}}
- **{{system_name}}** *(integration)* — {{what it provides or consumes}}
{{/for each}}

## Goals and outcomes

What success looks like, derived from positive end events.

- {{end_event_name}}: {{narrative meaning}}
- ...

### Non-goals

{{If the diagram contains explicit boundary conditions or "out of scope"
annotations, list them. Otherwise omit.}}

## User journey

The main path through the process, narrated as a story rather than as steps.

{{Replace numbered steps with a flowing narrative. Use the actor names as
characters. Example:

"The customer submits a loan application through the web portal. A loan
officer at the bank receives it the next morning and reviews it against
current credit guidelines. If the credit score is above 700, the officer
forwards the application to a branch manager for sign-off; otherwise, the
applicant receives an automated rejection within the hour. Approved
applications are funded within two business days."}}

## Edge cases and decision points

For each gateway, restate the decision in product language.

- **{{Decision name}}**: {{condition restated for non-engineers}}. If yes →
  {{outcome}}; if no → {{outcome}}.
- ...

## Exception handling

For each boundary event, restate as a "what if" scenario.

- **What if {{condition}}?** {{Restate the boundary handler in user-friendly language.}}
- ...

## Dependencies

External systems and integrations the process relies on.

- **{{system_name}}** — {{what we need from them, what they need from us}}
- ...

## Success metrics

Derived from end events. The PRD author should refine these.

- **Completion rate** — % of started processes that reach a positive end event
- **Time to completion** — median time from start to end
- **Failure rate** — % of started processes that reach an error end event
- {{Add more specific to the process if obvious}}

## Out of scope / open questions

{{Anything ambiguous in the diagram: unnamed elements, missing decision criteria,
unclear data schemas. The PRD is the right place to surface these to a PM.}}

---

*Generated by `bpmnemonic`. The diagram is the source of truth — re-run this
when the .bpmn file changes.*
```

## Notes on style

- **Specs.md** is exhaustive. Number every step. Cross-reference every gateway. Surface every ambiguity. The reader is implementing.
- **PRD.md** is selective. Tell a story. The reader is approving or funding.
- **Both** preserve the BPMN element IDs as comments so a future regeneration can detect drift.
- **Both** end with an "open questions" section. Diagrams are usually incomplete; honesty about the gaps is more valuable than confident invention.
